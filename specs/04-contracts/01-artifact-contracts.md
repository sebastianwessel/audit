# Artifact contracts

All CLI inputs, model outputs, tool inputs/outputs, and persisted artifacts are strict Zod schemas owned by their feature under src/features/. Universal primitives belong under src/shared/contracts/. Types come from z.infer. Zod contracts and their colocated contract tests are the sole maintained schema representation; generated JSON Schema mirrors are not retained. The shared model-route identifier schema owns every persisted provider/model label; configuration alone adds the configured-provider allowlist. Closed enums are normalized from case/whitespace variants at the boundary; unknown keys and values fail. Per-field text validation protects a boundary but must never silently cap an approved source/context corpus, range, search result, workflow traversal, complete tool glob set, source path, lineage entry set, evaluator result/readiness collection, or evaluator-only acquisition metadata collection. Safe path validation is single-owned by the shared relative-path schema and permits every non-empty slash-delimited relative path without traversal, backslashes, or NUL. Finite closed-enum projections may be structurally exact; they are not evidence ceilings.

`ArtifactTextSchema` is the one shared normalization boundary for persistable,
human-readable plan text. It removes unsafe terminal controls and replaces
recognizable credentials and direct PII literals with typed redaction markers
before any plan/draft/public-projection schema accepts the value or derives an
identity. It applies to labels, titles, rationales, risk statements, evidence
requirements, and limitations; it does not inspect, truncate, or partition
approved source or context. Pattern recognition is defence in depth only: the
source-minimal artifact model remains the publication boundary, and no source
or raw model text is retained as protected detail.

## Configuration

Each CLI command validates its own closed option set before loading configuration, opening a root, reading an artifact, constructing a provider, or dispatching a model. Unknown and command-incompatible options fail as invalid input; no option is silently ignored. It then validates target, public artifact, private work, context, source-admission policy, and limit arguments at its own boundary. Target, context, public artifact, and private work roots are canonical non-symlink directories that are pairwise disjoint before any I/O other than root canonicalization. No root may be equal to, an ancestor of, or a descendant of any other root. Public artifacts contain only publishable source-minimal projections; private work contains snapshots, checkpoints, locks, and evaluator work. The v1 target network policy is always deny; no plan or model can change it. The platform `RuntimeConfigurationDefaults` is the sole owner of the default OpenAI / `gpt-5.6-terra` primary route, artifact/evaluation roots, same-route verification mode, and positive `maxParallelVectors` rate-limit queue. `RuntimeConfigurationSchema` applies those defaults and accepts optional environment overrides plus an optional API-key environment-variable name. The queue limits only simultaneous independent work; queued vectors remain required and are never omitted. Provider is openai or anthropic. Cost pricing resolves only from the generated bundled catalogue using the resolved exact provider/model pair; unknown entries yield a visible `unavailable` cost result rather than a zero estimate. Price values are not runtime configuration.

Local runtime defaults are loaded only by the platform configuration adapter from an optional project-root `.env`. Normal model-backed setup needs only the credential for the default route; every `AUDIT_*` configuration value is an optional override. Its closed configuration shape contains the resolved provider/model, optional API-key environment-variable name, separate public-artifact/private-work roots, and evaluation paths. `AUDIT_PUBLIC_ARTIFACT_DIR` and `AUDIT_PRIVATE_WORK_DIR` replace the retired single artifact-root variable; the retired variable is rejected. `verificationMode` is `same-route` by default or an evaluation-only `independent-route`. The latter requires a complete distinct verifier provider/model pair and a named secret environment variable; it never stores the secret value. Incomplete or equivalent normalized route pairs fail before target I/O. Product commands reject this experimental mode. Precedence is built-in defaults, inherited environment, then `.env`; CLI inputs select an operation but never override runtime configuration. Empty values mean unset. The loader validates dotenv syntax, does not log values, and does not persist credentials in any artifact.

`ContextDocumentSchema` requires a relative path, title, `kind`, sensitivity, applies-to globs, Markdown body, and content digest. `kind` is one of `architecture`, `deployment`, `data-flow`, `controls`, `threat-model`, or `other`; sensitivity is `public`, `internal`, `confidential`, or `restricted`. The frontmatter parser rejects unknown keys, duplicate keys, malformed delimiters, unsupported YAML constructs, invalid globs, and non-UTF-8 content. It preserves the Markdown body byte-for-byte after the frontmatter delimiter, including leading/trailing whitespace and line-ending form; only an all-whitespace body is invalid. There is no fixed context-document count, metadata-list, or body-size ceiling. Context discovery accepts the `.md` extension case-insensitively. A provider-signalled context recovery chunk preserves the exact concatenation of its original body; it may not trim or normalize line endings. Body text is never interpreted as executable instructions.

The validated target inventory contains sorted context documents and a context digest. The planner and auditor receive context documents in a separate labeled section from source evidence. Context may explain a claim or identify a security control, but source evidence remains required for a finding and context cannot change permissions, approval status, network policy, or scope.

## Snapshot and plan

`SourceAdmissionPolicySchema` owns named include/exclude policy and default-exclusion reasons. It rejects arbitrary maxima for files, bytes, lines, matches, context bodies, or tools. `SourceSnapshotManifestSchema` contains sorted manifest rows and the derived target fingerprint. Each row is either one admitted regular UTF-8 file with normalized relative path, byte length, content digest, and private snapshot-object reference, or one excluded entry with a closed reason. A source snapshot is built through exact streaming byte transactions; it never concatenates the corpus or rereads mutable target content after its digest is accepted. Context is separately digested and preserves line endings. Publication of private source/context objects and the target-keyed `SourceSnapshotRetentionIndexSchema` mutation use the same exclusive lease; release uses that same lease and removes the snapshot directory only after the final run/context owner is removed.

## Plan

AttackPlanSchema requires schemaVersion, planId, planDigest, target snapshot identity, context digest, createdAt, inventorySummary, executable vectors, and `additionalObservations`. target is rootFingerprint plus bounded displayName. An additional observation is a uniquely identified source-aware suggestion for human plan review: it has scope, obligations, rationale, and limitations but no enabled state, finding, category, priority, impact, exploitability, or fix. It is part of the sealed plan identity and Markdown projection, but never an executable audit vector. Human plan review, ownership, approval, and change-management records are external to the product and are not accepted in this contract. inventorySummary is a projection of the snapshot manifest.

Every persistable plan-text field crosses `ArtifactTextSchema` before vector or
plan digests are derived. `plan-draft` and `plan-reseal` use the same schema, so
a human edit is normalized before it becomes a new sealed identity. A historic
plan whose raw text no longer agrees with the normalized digest is rejected and
must be resealed; no legacy reader or migration preserves the unsafe form.

AttackPlanDraftSchema is the sole editable plan contract. It contains only its schema version, exact basePlanId/basePlanDigest, editable `DraftAttackVectorSchema` values, editable non-executable observations, and exact `promotedObservationIds`. It deliberately excludes target/context fingerprints, inventory summary, display metadata, timestamps, vector IDs, vector digests, plan ID, and plan digest. `plan-draft` creates it from a sealed base plan; `plan-reseal` requires the exact base binding, validates every changed vector through the shared draft-vector schema, rejects no-op edits, and derives a new AttackPlanSchema artifact. Promotion may select each exact base observation once only; it converts that base suggestion into a new enabled vector and removes it from retained suggestions. An unpromoted observation cannot execute, create a finding, receive a priority/fix, alter coverage, enter a CI decision, or affect evaluation scoring. A sealed plan JSON, Markdown projection, and YAML document are never accepted as an editable or executable substitute. Every sealed plan, Markdown projection, and draft is a private-work artifact for local human review; no product command publishes it below the public artifact root. Immutable plan/draft writes fail if their destination already exists; the product does not overwrite a prior plan artifact.

AttackVectorSchema requires vectorId, vectorDigest, title, rationale, enabled, scopeGlobs, explicit risk-positive reviewObligations, and limitations. Its title is only a human-readable review focus; it is neither a taxonomy label nor an urgency judgment. A review obligation has a stable obligationId, riskStatement, and evidenceRequirement; its id is unique inside the vector. `riskStatement` names the source condition and protected security consequence under review; `evidenceRequirement` names the source relations and controls required to establish or negate that exact concern. These are the sole human/model semantic fields: deterministic validation preserves their exact text but does not parse or infer their meaning. Each vector has at least one obligation. `vectorDigest` is SHA-256 over every behavior-affecting vector field; `vectorId` is its stable projection. `planDigest` is SHA-256 over canonical plan behavior plus target snapshot and context identity; `planId` is its stable projection. Timestamps and display metadata do not affect either digest. Duplicate vector IDs/digests, duplicate obligation IDs, and zero enabled vectors fail. Human editing requires explicit validate/reseal and always produces a new identity. scopeGlobs are evaluated against normalized admitted snapshot paths; an empty match is a visible execution state, never an unrestricted fallback or deterministic clean result. Retired category and priority fields are rejected rather than converted.

`SourceEvidenceRoleSchema` is single-owned by attack planning and reused by report, investigation, and verification contracts. Its values are `entrypoint`, `operation`, `unsafe-condition`, `source`, `sink`, `guard`, `dataflow`, `root-control`, and `counterevidence`; all are normalized model tokens and organize source-backed explanation only. Its `ClaimEvidenceRoleSchema` subset is the sole shared owner of the required relational roles `operation` and `unsafe-condition`, reused by candidate, narrative, verification, and evaluator contracts. Evidence-map facts use their own neutral role vocabulary, which additionally permits `entrypoint` beside input, asset, boundary, operation, control, output, and assumption. No contract creates or admits a synthetic origin-to-operation path: role labels and explicit map references organize provenance only and are never security proof.

`AuditReportLineageSchema` is a strict schema version 2 owned by `audit-lineage/`. It has `lineageId`, `generatedAt`, previous/current report identities (`reportId`, `planId`, `targetFingerprint`), aggregate status counts, and a complete sorted entry list with no product cardinality ceiling. An entry has opaque `findingIdentity`, nullable prior/current scan-local `findingId`, nullable prior/current `vectorId`, a `new|persisting|resolved|unknown` status, and an exact closed reason token. Its identity is a source-free cross-scan fingerprint over vector, approved obligations, evidence roles/paths/kinds, and evidence-content hashes; the scan-local identity additionally includes ranges. Both exclude model claim wording. A collision is rejected rather than guessed. It contains no source path, source snippet, statement, limitation, prompt, model output, tool result, or credentials. Reports must reject duplicate coverage vector IDs and duplicate deterministic finding IDs so lineage never arbitrarily selects an input record.

The model produces one executable plan. The product does not define approval, rejected, reviewer, or review-note fields. The constrained external AttackPlanDraftSchema is an authoring transport, not approval state or model input.

## Evidence, finding, report

Evidence references require a relative path, positive startLine, optional endLine not below startLine, SHA-256 content digest of the exact selected source line, and kind source, configuration, context, or inventory. The source line exists only in the transient jailed read transaction. Public reports, CI projections, lineage, and telemetry never persist or render a source/context snippet, prompt, raw model response, verifier reason, error message, or provider metadata. A finding may retain only its canonical, validated, artifact-text-redacted `ClaimNarrative`: one claim statement, one explanation per selected evidence role, and declared limitations. The narrative is human-facing context, never evidence, provenance, admission input, identity input, source excerpt, or a verifier rationale. `PublicAuditReportSchema` v4 additionally projects the sealed plan's vector title and exact obligation risk/evidence requirement after artifact-text redaction, solely to make the already-approved review question understandable; this is presentation context, not a finding, classification, urgency, remediation, or a new model decision. It retains closed vector-coverage limitation codes, closed not-applicable reason codes, and only the exact source-minimal evidence selections of the posture's already-selected map facts. Pattern redaction is defence in depth, never a publication boundary.

`EvidenceMapSchema` holds neutral source-backed facts, controls, unanswered obligations, and limitations for one vector; it is neither a finding nor a deterministic security rule. Its model-facing candidate is a closed bounded untrusted map: a fact carries a schema-valid identifier, closed neutral role, bounded statement, plan references, and one-or-more exact `{path,startLine}` selections. It also carries exactly one `controlCoverage` entry per approved obligation. Each entry lists the distinct `controlFactIds` that the mapper associated with that obligation. Every downstream map-fact reference collection and unanswered-obligation collection is a unique set: a duplicate cannot replace a required fact through length or membership comparisons. In a canonical map, an obligation is either mapped or unanswered, never both. Model-bound overlap is normalized only by discarding the unanswered declaration after a retained validated fact maps that same obligation; it never persists a contradictory state. Map integrity validates each selection against scoped transient source, then projects the canonical content digest, kind, and one-line range; it quarantines a fact with an invalid plan, duplicate identifier, path, or line and fails coverage when an entry is missing or does not exactly match the retained neutral control facts. It cannot carry a snippet, source kind, evidence role, end line, or model-authored provenance metadata. The stage never promotes an unrecognized role or an out-of-plan reference by normalization. `SourceEvidenceSchema` is the sole owner of persisted source-evidence digest, kind, role, and optional end-line representation. It applies the shared model-token normalization and explicit optional-null normalization at canonical model boundaries, then persists only canonical lowercase tokens and omitted optional values; mapping, investigation, and verification never implement separate formatting rules.

Every persisted obligation-closure row binds its repeated obligation identifier to the same canonical plan reference. Its map state, fact count, posture conclusion/reason, candidate count, admitted-finding count, and terminal disposition must be mutually consistent. Vector coverage then conserves these rows: map facts are bounded by the closure references that retain them, unanswered and posture counters equal their closure projections, admitted findings are represented by a closure, and the admission funnel equals the vector finding count when present. A vector result must exactly match its persisted finding and review-required arrays; a report must exactly match each coverage row to same-vector report entries and may not retain an entry for an uncovered vector. These are provenance and artifact-integrity checks only; they never infer a risk, source flow, exploitability, severity, or control effectiveness.

`SourcePostureSchema` is the sole shape for one candidate-blind conclusion (`risk-supported`, `risk-contradicted`, `inconclusive`, or `not-applicable`) per approved review obligation. A `not-applicable` conclusion carries exactly one closed reason: `no-relevant-operation-in-scope` or `external-component-not-represented-in-scope`. It is neutral: it is neither a finding nor a passed check. Every other conclusion omits that reason. Its cited map facts must include every retained neutral `control` fact for that same obligation. The obligation closure deterministically retains every evidence reference from those cited facts when and only when the conclusion is `not-applicable`; missing or extra references reject the closure. A discovery seed is non-reportable and carries only exact vector/obligation identity, map facts, posture assessments, a bounded hypothesis, and limitations. Grounding returns exactly one paired candidate, `no-source-backed-candidate`, or `map-insufficient` result per seed. Every raw result requires `nullReason`: it is `null` for a paired candidate and otherwise exactly one closed null reason. A non-null model candidate contains only its statement and role-selection bundles; canonicalization derives vector, exact obligations, inherited map references, posture projection, and limitations from the paired seed. A `map-insufficient` result must be joined to one-or-more closed generic map insufficiencies for the seed's exact approved obligations.

A non-null candidate and an accepted verifier result carry exactly two `ClaimEvidenceBundle` values, one `operation` and one `unsafe-condition`. Each bundle has one-or-more unique map selections and an artifact-safe explanation of that role. The roles may use the same map fact only through distinct evidence items. Grounding's model-facing contract contains only the statement and those bundles; the canonical materializer forms the exact candidate map basis as the seed's inherited set plus selected facts, rejecting a selected fact outside the seed's approved obligations. Canonical projection retains every selected source location; no primary location is substituted. The grounding identity and verifier materializer validate provenance, scope, cardinality closure, and exact projection only. They never decide whether a relation is unsafe.

`AuditVerificationResultSchema` is a strict decision-specific union. `accepted` requires both claim bundles, the exact complete hypothesis obligations, complete resolved obligation and posture reconciliations, and a source-backed control assessment. `rejected` requires a closed `effective-control` or `claim-contradicted` reason code, one-or-more projected contradiction/counterevidence locations, every affected exact plan obligation, and complete resolved reconciliations; it is a completed negative decision, not an operational error. `incomplete` has one closed evidence/scope/context/output gap reason and may retain inspected evidence but no claim, contradiction, control assessment, or reconciliation. Every model-facing decision branch must state its complete strict-object shape, including required `null` and empty-array fields; instructions must not imply that those fields may be omitted. A rejected response without valid projected contradiction evidence is incomplete. Accepted, rejected, and incomplete results retain only closed reason tokens and source-minimal evidence references; model rationale is transient and never an artifact field. The terminal reducer is the sole owner of vector closure, report outcome text, machine outcome, exit code, and evaluator status. An `inconclusive` posture remains incomplete unless a later valid accepted or rejected decision resolves that exact obligation.

`AuditEvidenceMapDraftSchema` v5 persists the validated source-minimal neutral map, its exact fingerprint, and an append-only candidate-blind repair ledger. `AuditSourcePostureDraftSchema` v4 is reusable only when its required evidence-map fingerprint equals the current canonical map. A canonical map fact may retain only its validated artifact-text-redacted `summary`; a canonical posture assessment may retain only its validated artifact-text-redacted `summary`. These summaries provide bounded semantic context to later scoped model stages, are included in their exact dependency fingerprints, and are never source evidence, provenance, deterministic admission input, finding identity, raw model output, source excerpt, or public-report content. Candidate-grounding draft v10 additionally binds that same map and the canonical source-posture fingerprint, then persists exactly one canonical `grounded`, `no-source-backed-candidate`, `map-insufficient`, or `binding-rejected` outcome per seed, validated closures, the complete source-free discovery-to-grounding funnel, the complete canonical-candidate rejection ledger, and required content-free discovery/grounding observations. Canonical candidates are derived solely from those grounded outcomes; no duplicate candidate list is persisted. A resumed verifier projects those same ledgers and observations into terminal coverage. Discovery seeds and raw grounding output never persist. Candidate-aware checkpoint v5 independently repeats the exact candidate, map, and posture fingerprints, so a completed verifier or countercheck result is never reused after either predecessor changes. AuditReport v20 carries source-free discovery-to-grounding attrition and every candidate-blind evidence-map-repair stage observation beside the closure matrix. Its conservation rule is discovered seeds = discovery-binding rejections + grounding no-source-backed-candidate outcomes + grounding map-insufficient outcomes + grounding binding rejections + submitted candidates. A candidate and persisted finding contain only approved obligations, complete selected evidence bundles, closed decision/gap tokens, source-minimal evidence references, and the validated artifact-text-redacted `ClaimNarrative`; arbitrary raw model statements, verifier rationale, category, priority, confidence, impact, and proposed fix are absent. Its `errors` retain only closed code, stage, and retryability; finding verification retains only closed status and integrity checks. The synthesis owner creates the run-local identity (including every evidence range) for report rows, coverage, funnel counts, evaluator keys, and duplicate collapse, and the range-free fingerprint for lineage only. Exact duplicates merge only deterministic sets and increment `duplicateCollapsedCount`; a conflicting exact identity fails closed with `finding-identity-conflict`. The admission funnel conserves reconciled verifier results as post-verification rejected + duplicate collapsed + admitted. A persisted report item is either `accepted` with `verified` evidence or `needs-review` with `insufficient-evidence`; no legacy candidate/dismissed item or inferred cross-finding chain is representable. Both its own and every terminal vector result's required `reviewRequired` collection are distinct from `findings`: every item is source-minimal and cannot share an identifier with an accepted finding. It represents a structurally accepted candidate-aware result that conflicts with relevant candidate-blind posture and never contributes to CI finding status. Older plan/report/checkpoint artifacts are rejected rather than translated.

`DeveloperGuidanceReportSchema` v3 is a separately persisted, non-gating companion artifact. It binds its own identity, run id, plan/report ids and digests, target/context fingerprints, one stable accepted-finding binding per item, and a content-free aggregate model observation. A binding contains only the accepted finding id/fingerprint and vector id. Each item is either `completed`, retaining only advisory priority, `incomplete` with a stable reason code, or `cancelled` with `provider-cancelled`. Model-authored rationale, impact, remediation, validation steps, and limitations are transient only and are never persisted. Guidance is created only after the sealed plan, report, and fresh target/context inventory agree. Its stage may inspect only the finding's original vector scope. It cannot change a report, finding identity, evidence, coverage, lineage, evaluation result, or CI exit code; it is not a proof of exploitability or a patch-application instruction. The JSON is the strict artifact and its Markdown companion is a deterministic human projection: completed items direct the owning team to review accepted evidence and plan obligations, then choose and validate an appropriate mitigation through normal change management. Neither is an executable plan input. `DeveloperGuidanceCheckpointSchema` v3 persists each terminal item and its source-free stage observation after every finding attempt. Reuse requires exact run, report, plan, target/context, provider, model, and guidance-protocol binding; a mismatch is rejected. Checkpoints are partial progress, never audit reports, and a resumed run dispatches only unfinished accepted findings. Because advice prose cannot be losslessly reduced without persistence, `context_length_exceeded` is explicit incomplete guidance coverage; it is never partitioned or merged.

`AuditCheckpointBindingSchema` binds run ID, exact plan/vector digests, target snapshot/context identity, provider/model/verifier route, phase, and every applicable prompt/tool protocol fingerprint. A terminal checkpoint additionally binds the aggregate of its contributing phase protocol fingerprints. A map draft is reusable only to retry posture, discovery, grounding, or verification; a posture draft only when its map fingerprint matches and only to retry discovery, grounding, or verification; a candidate-grounding draft only when its map and posture fingerprints match and only to retry verification; a candidate-aware checkpoint repeats and validates those exact map and posture fingerprints beside its candidate fingerprint; a terminal result is reusable only after all binding values match. Grounding reuse additionally requires the complete prompt-protocol fingerprint. A schema-v3 context-overflow topology ledger additionally binds its reducible phase, stage id, opaque phase-input fingerprint, root scope hash, and recovery-protocol fingerprint. The phase-input fingerprint represents the complete source-free predecessor state consumed by that phase; an evidence-map repair or posture recomputation changes it, making stale descendant topology, leaves, and candidate-aware checkpoints ineligible for reuse. Each terminal event carries exactly one execution union: `{ kind: provider, modelObservation }` or `{ kind: deterministic }`; an overflowed, failed, or cancelled child cannot be deterministic. Every schema-v3 recovery leaf has `recoveryState: partial` and the same exact execution union. `AuditEvidenceMapRecoveryLeafSchema`, including its separately phase-named `evidence-map-repair` leaf path, `AuditSourcePostureRecoveryLeafSchema`, and `AuditCandidateGroundingRecoveryLeafSchema` bind that same identity plus their parent stage, recovery protocol, root scope, child identity, and child scope hash. Candidate-aware verifier/countercheck topology carries the derived phase-input fingerprint over its phase, exact candidate, map, and posture identities. Map/posture leaves hold only validated redacted local phase fragments, never vector-wide closure. A grounding leaf holds exactly one canonical `grounded`, `null`, or `binding-rejected` result per ephemeral seed after source validation; it holds neither the seed nor raw model selectors. Every leaf is written before the matching topology completion event and is reusable only when that matching completed event exists with byte-identical execution telemetry. No topology or leaf artifact persists paths, ranges, context digests/bodies, prompts, tool data, source, or raw model output. Discovery seeds and raw grounding output are not artifacts. Older versions cannot be silently reused.

## Read-only tool shapes

`repo_list` input has optional `includeGlobs` and `excludeGlobs`; omission normalizes to `['**/*']` and `[]`, respectively, so it lists every file in the already approved scope. Its output is the complete sorted admitted snapshot entries with relative path, sizeBytes, and optional languageHint. `repo_read` input is relative path, optional startLine, and optional endLine; output is the complete requested snapshot range as ordered strict `{ line, text }` physical-line records, where each `line` is the actual one-based source coordinate. The former unnumbered text response is rejected. Exact evidence-map and verifier selections may cite only returned `repo_read` line values; `repo_grep` may locate candidate regions but cannot supply a coordinate by inference. `repo_grep` input is pattern, mode literal/identifier/regex, caseSensitive, optional relative paths, and optional nonnegative `contextLines`; the latter forwards surrounding-line context to the jailed tool and has no product maximum. Its output is complete scoped snapshot matches. Identifier mode matches only language-neutral identifier boundaries. The review-workflow tool-contract module is the single model-facing owner for all three shapes and descriptions. Every tool object is strict and every output is validated before the model sees it. A stage records aggregate file-tool usage but has no fixed product call or return cap that can omit approved evidence. Execution budgets contain only run timeout, model timeout, and retry mode; `0` disables a deadline, positive deadlines are operator-selected operational stops, and unknown fields are rejected.

Markdown is a deterministic projection of validated JSON. It renders every persisted finding-evidence reference with its role, location, and content digest; it may not select only a primary evidence item or display source/context text. Operational rows are complete and deterministically ordered rather than truncated to a presentation count. Every artifact carries a schema version; the canonical registry above governs persisted artifact versions. All earlier plan/report/checkpoint artifacts are rejected rather than translated.

Human-facing report clarity is a deterministic projection concern. Every audit Markdown projection renders sealed vector/obligation context for findings and closure rows, one complete per-vector **What to do next** table, and a dedicated neutral **Not applicable** section before the technical appendix. It uses exact closed wording: `no-relevant-operation-in-scope` means “The reviewed scope contains no operation relevant to this obligation”; `external-component-not-represented-in-scope` means “The reviewed source shows this obligation belongs to a component not represented in this scope.” Each row includes only its selected source-minimal references. The renderer must not derive wording, an action, or a security conclusion from source evidence, limitations, claims, classifications, urgency, answer keys, raw model text, or fixture knowledge. `completed` directs ordinary report review; `not-applicable` directs retention as a neutral outcome rather than a pass; `skipped` directs plan-configuration review when coverage is required; and `incomplete`, `failed`, or `cancelled` direct explicit same-run recovery or investigation and prohibit treating the vector as covered. The row does not alter terminal classification, CI status, checkpoint reuse, or product admission.

Every real-world evaluation Markdown projection renders an **Evidence strength** block before quality-looking metrics. It reports six separately labelled dimensions from already-persisted run state: operational completion; semantic-plan measurement availability; finding-measurement applicability and completed-trial scope; precision availability from finding-label coverage; corpus evidence qualification; and verifier-route independence. A generated-plan path-reachability result is never rendered as semantic-plan measurement. A generated-plan trial records one evaluator-only semantic state after product closure: completed score, incomplete/cancelled measurement, or not reached with a stable reason. An audit-reviewed-plan profile is `not applicable` for generated-plan semantics. A same-route verifier is explicitly non-independent. The block is explanatory only: it neither creates a score nor changes a run, checkpoint, baseline, comparison, or gate.

## Evaluation contracts

`EvaluationPackSchema` requires a pack id/version, supported track, fixture roots, case ids, provenance entries, license status, and a digest of the answer-key directory. `EvaluationCaseSchema` requires a case id, language, difficulty, fixture path, expected locations or location ranges, and adjudication notes. The model-facing target view is generated without expected fields and is validated as a separate `EvaluationAgentInputSchema`.

`CorpusCandidateRegistrySchema` is a separate strict, digest-bound acquisition contract. Its source record and each candidate contain only repository URL, vulnerable/patched revisions, metadata path/digest, and observed upstream source-license status. Candidate records are repository-distinct and ordered. They contain no target source, source-snapshot state, human-adjudication state, expected security category, location, plan, answer key, score, readiness state, or model-visible path. Local upstream verification checks the exact pinned metadata record without network access; it cannot promote a candidate into a corpus case. `AcquiredSourcePairSchema` is the separate complete-tree provenance artifact and sole acquired-snapshot state: a valid workspace root contains only its strict manifest plus the declared `vulnerable` and `patched` regular-file trees. Aggregate acquisition validation rechecks every workspace byte/mode and rejects duplicate snapshot or registry/candidate identities; its summaries are content-free and cannot alter candidate, corpus, or readiness state.

`EvaluationRunSchema` v13 and `ProviderEvaluationCheckpointSchema` v14 reject earlier ambiguous shapes. Both bind the complete selected `(caseId, variant, repetition)` population in addition to its digest. Terminal run trials must contain every selected identity exactly once and no other identity; duplicate, missing, or invented identities reject the artifact before reporting, scoring, baselining, or comparison. Every v13 trial records exactly one semantic-plan measurement state. The run derives, rather than accepts, its three-dimensional measurement state from those terminals: workflow completion, semantic-plan completion/non-applicability, and finding-measurement completion/non-applicability. Checkpoint resume compares that exact population before provider construction or dispatch. The checkpoint lifecycle is `created -> running -> finalizing -> completed`, with explicit `failed` and `cancelled` terminals. `finalizing` freezes the complete source-free run/report/digest payload and is prohibited from dispatching a model. Reliability summaries retain all-terminal and completed-only latency percentiles separately; a failed or incomplete trial is never silently omitted from the all-terminal view. Every command invocation appends one immutable attempt record with its mode, terminal state, source-free failure codes, new/reused dispatch counts, observed cost, model duration, finalization duration, and distinct latest/cumulative active wall durations. A failed `artifact-publication` checkpoint additionally carries exactly one closed `publicationReason` (`terminal-destination-occupied`, `staging-directory-invalid`, `rename-failed`, or `publication-unknown`); no other failure domain may carry that field. Only `rename-failed` may record `resume-finalization`; every other publication reason, and terminal artifact validation during publication, requires `operator-action-required`. The command captures its attempt baseline before dispatch and uses that immutable baseline for both successful and failed terminalization, so attempt-local work and cost never appear as reused work.

`StageIsolatedEvaluationStagePack` v3 and its checkpoint/result artifacts are evaluator-only contracts. A pack binds exactly one profile, stage, selected trial, corpus/source/context identity, product/evaluator protocol, route, provider/model, canonical input, and expectation reference. Its semantic evaluator receives only an unpersisted, feature-owned safe projection of the validated product result plus the evaluator-private rubric. That projection uses opaque output/localization identities and selected source-free semantic claims; it excludes source, paths, ranges, snippets, prompts, tool data, raw model output, answer-key labels, classification, urgency, and remediation. It is never a callback, static matcher, generic serialized product object, or product-admission input. A forensic result separates product completion from semantic measurement: a completed product stage followed by evaluator failure/cancellation keeps the product observation while its semantic state is `incomplete`/`cancelled`. The evaluator observation is separate from product-stage observations. Checkpoints retain only sealed evaluator-private identities and source-free count/identity projections; they never retain the packet, raw product result, or source locations. Their public result projection is source-free and aggregate-only. Canonical-input fingerprints are derived by the feature-owned strict schema, never accepted as caller assertions. Checkpoint states are `running`, `completed`, `incomplete`, `failed`, and `cancelled`; exact binding is checked before provider construction or dispatch. Public results expose semantic outcome/localization counts only for completed adjudication and separately report product/evaluator telemetry. They never expose target paths/ranges, fact/seed/candidate/expectation identifiers, source, prompt, tool payload, packet data, or raw model content. A dedicated stage-comparison artifact rejects any mismatch in stage/profile/trial/corpus/source/context/protocol/route/expected denominator, and is not comparable with a normal evaluation run. v2 stage-isolated artifacts are rejected without a compatibility reader or migration.

Provider terminal publication is a separate contract. Every mutable evaluator artifact—including generated-plan, semantic-plan, audit, and expected-evidence checkpoints—lives only below the private evaluator work root. The public run directory is reserved exclusively for the frozen `evaluation-run.json`, Markdown report, trial trace, and versioned terminal manifest. The command stages the terminal set below the work root, validates its aggregate/population bindings and byte digests, then publishes the complete directory by one same-filesystem rename. A checkpoint becomes `completed` only after the visible manifest revalidates. A fresh run rejects an occupied terminal directory; an explicit finalization resume first revalidates an already-published matching directory and otherwise republishes the frozen set without constructing or calling a provider. Failures retain a typed source-free domain (`configuration`, `corpus-validation`, `provider`, `provider-cancelled`, `model-contract`, `audit-workflow`, `checkpoint-persistence`, `artifact-validation`, `artifact-publication`, `lock-conflict`, or `operator-stop`) and never recast persistence/publication work as a provider failure. `PathReachabilityScore` is immediate scope reachability only, never semantic plan quality. An end-to-end-generated trial may retain a source-free evaluator-only expected-role loss trace through planning scope, neutral mapping, posture, validated discovery, grounding, verification, and terminal coverage. Each row has only an evaluator finding identifier, role token, booleans, and first-loss token; it excludes locations, facts, assessment ids, seeds, candidates, prompts, tool data, model content, model input, scores, and product admission. Its separately persisted evaluator-work checkpoint binds the exact trial, sealed plan, target/context, provider/model/route, prompt protocol, and answer-key digest; it rejects a mismatch and never writes raw discovery seeds. The qualification is separate from and cannot be inferred from the workflow finding gate. A private-holdout checkpoint and run additionally store one minimal `HoldoutAttestationReference` (attestation id, canonical payload digest, public-key fingerprint, issued-at time). The full strict attestation envelope is source-free and requires schema version, issuer, exact holdout pack id/version/manifest digest, full-readiness-report digest, Ed25519 signature, and matching public-key fingerprint. Before any provider call, the CLI reads regular non-symlink attestation/key files, verifies the key type, manifest binding, and signature; private keys never enter the product. The reference is included in configuration and comparison identities so a changed authorization cannot resume or compare as the same measurement. An optional observed-cost ceiling is intentionally outside the provider-evaluation configuration fingerprint: it is an operational stop condition, not a quality/protocol variable. Resume seeds its ceiling ledger from completed prior-trial observations, permits a changed ceiling, and never compares a ceiling value as quality evidence. Each completed or failed provider trial carries its source-free model usage/cost observation, and the run aggregates it. Completed trials retain the sum of their vector finding-admission funnels: candidates, terminal integrity/verification outcomes, and admitted findings. Finding scoring uses a stable maximum-cardinality one-to-one match between expected findings and actual findings, so overlapping early matches cannot hide later uniquely matchable expected issues. Targeted labels support recall and role-localization only; precision and F1 are null. The execution budget contains model timeout, run timeout, and retry mode; run timeout must be at least model timeout. Metrics are closed objects with explicit nullable fields; persisted evaluation artifacts do not use open records. The comparison contract is closed: a `same-route-regression` rejects changed provider/model, verification mode, route fingerprint, holdout attestation, finding-label coverage, prompt protocol, or vector concurrency; a `primary-model-experiment` allows only the sole primary provider/model and its corresponding same-route fingerprint to differ, requires `same-route` for both artifacts, and retains every other equality check. Comparison output separates adjudicated false-positive and unadjudicated-finding deltas. Neither kind can pass or fail an independent-route experiment without its own preregistered route-compatible baseline.

If a completed frozen run has unfinished trials, the only permitted reopening command is `--resume true --retry-unfinished true`. It first revalidates and atomically retains the current public terminal directory at `.provider-evaluations/<runId>/published-attempts/<attemptId>`. It cannot overwrite a retained attempt. It then reruns only unfinished trial work using the normal exact checkpoint bindings and publishes a replacement terminal directory only after the new frozen set validates. A crash after retention but before checkpoint persistence is safely repeatable because the retained attempt path is deterministic. The retained artifact set remains source-free.

The provider-evaluation preflight and one-case smoke command expose a normal async command result and an outer error boundary. Their executable entrypoints set `process.exitCode` only after that boundary returns; they never call `process.exit`. This permits pending `finally` cleanup, buffered source-free output, and checkpoint terminalization to complete. A command error prints only the existing safe error message and sets code `2`; no boundary logs credentials, source, prompts, tool data, or raw provider output.

`ProviderSmokeCheckpointSchema` v1 owns the one-case smoke command lifecycle. It binds run id, provider/model, selected case/variant, target/context fingerprints, reviewed-plan fingerprint, verifier/evidence-map/workflow protocols, and execution budget before audit dispatch. A run id must either start fresh with no checkpoint or resume that exact identity; it cannot overwrite or repurpose stopped work. Its source-free `running`, `completed`, `failed`, or `cancelled` state is distinct from the audited vector outcome. `ProviderSmokeRunSchema` v2 reuses that immutable identity and adds only terminal audit projection, timing, vector summaries, and aggregate model observation; it has no answer key, finding content, source, prompt, tool argument/result, raw model output, or secret.

### Semantic plan evaluator v5

`PlanSemanticAdjudicationSchema` v5 and `PlanSemanticEvaluationSchema` v5 bind the exact run/trial/case/variant/repetition, generated plan id/digest, target/context fingerprints, semantic-rubric digest, evaluator protocol fingerprint, and evaluator route. The semantic-rubric digest and model input contain only scenario id, objective, source-only applicability, required risk condition, and evidence requirements. They exclude answer-key relevant paths, expected-finding identifiers, source ranges, and all location-equivalent data; deterministic path reachability and terminal finding scoring retain those answer-key fields outside the evaluator call. The evaluation requires exactly one content-free `plan-semantic-adjudication` stage observation. `PlanSemanticAdjudicationCheckpointSchema` v4 repeats that complete identity for `running`, `completed`, `incomplete`, and `cancelled` states. A completed state contains the validated v5 evaluation; an incomplete or cancelled state contains only a normalized source-free error code and evaluator observation. Any binding mismatch rejects checkpoint reuse before provider construction or dispatch. The normal provider-evaluation lifecycle owns this operation and projects its terminal state into its exact trial; a standalone command, aggregate, or report artifact is prohibited. A completed checkpoint may be reused only by that exact runner binding. No semantic evaluator state changes product admission, finding scoring, external reliability, or provider-selection claims.

The real-world corpus answer key is evaluator-only. `CorpusAnswerKeySchema` version 6 carries case-level `staticReviewApplicable`, source-bound expected planning scenarios, `findingCoverage`, and role-specific accepted ranges into every independent review record. An expected planning scenario has a stable id, one-or-more relevant paths, and explicit expected-finding ids; each id must bind to an expected finding on one of those paths. Generated-plan scoring records scope coverage only and cannot claim semantic plan alignment from titles or labels. A `dual-reviewed` key contains exactly two distinct reviewer identities and exactly two human-review records. Both records must be `include` and must match the key's canonical judgment: finding-label coverage, exact scenario set, expected-finding set (id, role ranges, and applicability), patched expectation, and static-review applicability. A qualified dual-reviewed key must be source-only applicable and contain at least one expected vulnerable finding; a non-applicable or no-finding candidate remains provisional or excluded. Every `paired` corpus case must additionally declare `no-matching-finding` for the patched variant before it is evaluable. Reviewer identity, timestamp, notes, and array order do not affect agreement. An optional resolver preserves a disagreement record but cannot turn disagreeing records into a dual-reviewed key. Versions 1–5 are rejected rather than reinterpreted. These records never enter an agent target view, prompt, report evidence, or score input other than through the finalized answer key.

Ground truth is never mounted below the agent target root, included in context files, or passed through a harness tool. The scorer reads it through a trusted evaluator port after the agent run has ended. A pack with a missing, malformed, or target-visible answer key is invalid.
