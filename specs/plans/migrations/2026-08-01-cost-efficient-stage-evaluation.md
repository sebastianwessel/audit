# Cost-efficient stage evaluation and source-tool assistance

Status: implementation authorized by the product owner. This specification follows the diagnostic provider evaluations recorded on 2026-08-01.

## Problem and evidence

The final same-route reviewed-plan run completed 6 of 30 trials. All 25 evidence-map attempts used a scoped source tool, while later phases still produced explicit uninspected failures: 8 source-posture and 5 investigation terminals. Verification also produced incomplete terminal decisions. The run retained truthful coverage and did not silently score incomplete work, but repeating the entire corpus to test a small workflow change is unnecessarily costly.

## Decisions

1. Do not add a generic task, checklist, memory, shell, network, write, or edit tool to audit agents. A task-list tool is not source evidence and would compete with the three allowlisted read-only repository tools.
2. Keep `repo_list`, `repo_read`, and `repo_grep` as the complete model-visible tool surface. New source assistance may only be a strict, read-only composition of those same jailed operations; it cannot preclassify security meaning, filter eligible source, introduce a language rule, or return an uncapped inline source package.
3. Every source-deciding stage shares one explicit first-action instruction: when its scoped manifest is non-empty, it must call `repo_read` or `repo_grep` before considering an output. The shared lifecycle remains the sole enforcement: an uninspected completion retries only within the unchanged scope and then records `coverage-incomplete`.
4. Add a no-provider stage-conformance evaluation. It uses scripted provider/tool-loop fixtures to exercise mapping, posture, discovery, grounding, verification, and experimental countercheck independently. Its closed results are protocol conformance only: tool inspection, scope preservation, retry behavior, terminal state, and privacy. It has no answer key, security conclusion, model-quality score, or provider cost.
5. Provide a distinct provider smoke command. It accepts exactly one existing development case, one variant, one attempt, and `reviewed-plan`. Before provider construction it validates the selected source checksum and reviewed plan without opening an answer key, and requires an exact bundled price. An observed-cost guard is optional; when configured, it is a dispatch guard rather than an evidence, tool, output, or total-work cap. It emits phase observations, tool-use counts, terminal coverage, latency, and catalogue-derived cost. It must reject generated plans, repetitions other than one, baseline comparison, private holdout, and quality/reliability labels. It is an explicit opt-in diagnostic command and is never default CI. An explicit same-id resume reuses only exact-bound checkpoints; `--retry-unfinished true` is required before unfinished work can dispatch again.
6. `reviewed-plan` is the deterministic audit-only evaluation input. It is evaluator-owned, strict-schema validated, inventory-fingerprint bound, and isolated from answer keys and agent-visible files. Every reviewed-plan trial persists a canonical fixture fingerprint; generated-plan trials persist `null` instead. It may be changed only through corpus review; it never derives from a planning-provider response. `generated-plan` remains a separate planning-plus-audit profile. Aggregates and baselines never compare profiles.
7. Candidate-aware terminal diagnostics are a closed source-free operational contract. Each verifier or evaluation-only countercheck attempt records exactly one lane: `accepted`, `rejected`, `model-incomplete`, `evidence-projection-invalid`, `stage-failed`, `inspection-missing`, or `wrapper-contract-invalid`. A model-declared non-acceptance is distinct from an invalid deterministic projection or a stage/wrapper failure. The vector aggregates lane counts and proves they reconcile to the existing verifier accepted/rejected/incomplete funnel counts. Lanes contain no source, prompt, model reason, output selection, candidate identity, or security conclusion.
8. Candidate-aware verification receives one source-free canonical evidence-selection basis, derived from the admitted hypothesis, neutral evidence map, and candidate-relevant source posture. It lists only valid `{ factId, evidenceIndex }` selections for the hypothesis and exact obligation/posture reconciliations, plus required control fact identifiers and valid control selections. The verifier instruction and deterministic materializer consume this same basis. It is provenance and contract alignment only: it contains no source text, model output, security conclusion, origin-to-operation pointer, or semantic inference.

## Provider capability boundary

OpenAI Responses supports required tool choice, but applying it to every turn of a harness-managed tool loop can force further calls after evidence has already been read. The installed Purista harness exposes alias-level provider options rather than a safe initial-turn-only required-tool contract. v1 therefore does not pass raw `tool_choice` provider options or add a provider-specific bypass. A future initial-turn-only, provider-neutral capability requires its own spec, fake-provider contract, loop-termination proof, and a separate diagnostic comparison.

## Acceptance and measurement

- The deterministic stage suite fails if any non-empty scoped source-deciding stage can complete without `repo_read` or `repo_grep`, if retry expands scope, or if an unapproved tool is exposed.
- The provider smoke artifact has a new strict schema and is source-free. It contains no source, prompt, tool arguments/results, model output, answer key, credential, or request id.
- The provider smoke exit status represents only protocol completion. It cannot claim detection, precision, recall, false-positive rate, model quality, or release readiness.
- Every persisted candidate-aware terminal has one closed lane. The lane aggregates reconcile to the admission funnel; a malformed or thrown wrapper result is visible as `wrapper-contract-invalid`, never silently relabelled as model incompleteness.
- Audit-only provider evaluation loads the reviewed plan before dispatch, records its canonical fixture fingerprint, and records zero planning-stage calls. A fixture proves an answer key cannot construct or mutate that plan.
- A provider repeat experiment uses an explicitly recorded repeat count and runs only after a stage-conformance or smoke change indicates that a paid measurement is justified. Repeat count alone is not reliability evidence.

## Research record

Purista documents local, provider-neutral prompt helpers for fixed inputs and deterministic scoring, while leaving dataset/run ownership to the application. OpenAI documents `tool_choice: required`, including an allowed-tool mode. Those interfaces motivate the deterministic conformance suite but do not justify forcing tools on every loop turn. See [Purista prompt evaluation guide](https://github.com/puristajs/harness/blob/main/docs/guides/evaluating-prompts.md) and [OpenAI Responses tool choice reference](https://platform.openai.com/docs/api-reference/responses-streaming/response/custom_tool_call_input/delta?lang=javascript).

### Comparative design review

Codex Security demonstrates four compatible operational patterns: an isolated scan runtime, preflight before runtime/credential initialization, state and artifacts outside the reviewed repository, and an explicit incomplete-coverage exit that cannot be mistaken for a policy pass. Audit has those boundaries and retains its explicit incomplete terminal state. Its provider smoke command is a preflightable, output-root-only diagnostic with the same separation.

Codex Security's repeated discovery workers and VulnHunter's broad parallel trace agents are not adopted: they require materially higher cost, a different trust model, and make coverage accounting harder. The product has one approved-vector scope and a resumable phase lifecycle instead. Any future bounded parallelism must preserve one source-free closure row and one phase observation per obligation.

VulnHunter's useful transferable idea is disciplined falsification: navigation may locate relevant code, but a candidate survives only after a separate challenge reads source controls and counterevidence. Audit already expresses that without static language rules through neutral mapping, candidate-blind posture, candidate grounding, and verification. The following VulnHunter behavior is explicitly out of scope: executing code, installing dependencies, creating/running PoCs, writing fixes, shell/network tools, hard-coded language/file exclusions, and an exploitability admission requirement.

Neither product justifies a model-visible task-list tool. Each source-deciding input now receives one shared closed `inspectionRequirement` descriptor: `required: true` when its manifest is non-empty; allowed operations are exactly `repo_read` and `repo_grep`; and an inspection must precede every terminal result token. This descriptor is source-free protocol state, not a semantic rule, task store, tool, or bypass. It is owned once by the review-workflow tool contract and projected into mapping, posture, discovery, grounding, verification, and countercheck inputs. The shared lifecycle remains the only enforcement and telemetry owner.
