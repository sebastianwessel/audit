# Evidence and model-operations specification update

## Reason

The first live-provider seed baseline completed every trial but produced 2 true positives, 57 false positives, and 13 false negatives across 15 vulnerable trials, plus 21 findings on five patched trials. The report also showed that token and cost fields promised by the evaluation specification were not implemented.

## Contract changes

- Deterministic discovery results are renamed conceptually to clues and cannot persist as findings or survive a provider failure.
- A finding requires a verified investigator security claim and the category's required source-evidence roles.
- Source-free model usage, cost state, and provider cache-routing state are added to run/evaluation observations.
- Provider evaluation checkpoints remain outside the target and support deterministic reuse of completed trials plus opt-in retry of failed trials.

## Compatibility

Audit report schema version remains 2 because its persisted finding shape and approval semantics are unchanged; the `deterministicCandidateCount` field retains its wire name for compatibility while its meaning is clarified as a clue count. Run and evaluation observations add optional fields and older artifacts remain readable without treating absent usage as zero.

## Verification

- A static clue alone and a provider failure produce no finding.
- A model claim missing required source evidence is rejected with visible coverage/error accounting.
- Usage wrapper tests cover object/text calls, cached-token subset validation, cost calculation, unavailability, and no content persistence.
- Evaluation tests cover per-trial aggregation, checkpoint resume, and report projection.

Corpus readiness is now an explicit, content-free gate rather than an implied property of the mixed seed pack. This is a dataset-sufficiency result, not a provider-performance score.

The measured direct-flow/parser experiments are withdrawn as a production-design direction. They attempted to compensate for weak evidence reasoning by encoding narrow language and benchmark shapes in deterministic admission, which cannot make a language-agnostic reviewer understand arbitrary source. The replacement design makes the product a two-stage agentic review after human plan approval: a tool-guided investigator forms exact source-backed hypotheses, then a separate scoped verifier accepts, rejects, or marks each hypothesis incomplete. Deterministic code retains safety and integrity duties only—scope, path/line existence, redaction, phase binding, and state transitions—and no longer decides security semantics from a regex, parser, language hint, AST node, fixture, or answer key. Evaluation remains an independent guard that records evidence gaps; it must never generate a product rule or promotion claim.

## Countercheck admission design

The fresh tool-guided reviewed-plan baseline `reviewed-plan-prompt-protocol-baseline-20260729` completed 30/30 trials with the current prompt protocol, zero safety violations, 118 model calls, 186,751 input tokens, 20,898 output tokens, and a $0.587937 catalogue estimate. It still missed the only real-world vulnerable pair in every repeat and admitted patched findings in that pair and in the semantic-regression pair. The corpus is not reliability-ready, so this is a failure-mode signal rather than an effectiveness claim.

The countercheck experiment is not another seed-derived prompt, parser, rule, label, or category heuristic. It gives a verifier-accepted hypothesis to a separately mounted, source-scoped challenge agent with the approved vector, the same bounded path manifest, and advisory context. It may uphold, reject, or return incomplete; it may not create a hypothesis, broaden paths, alter category/priority, or use an answer key. It remains isolated from product admission unless a preregistered, repository-disjoint evaluation demonstrates a benefit.

The initial experimental run `reviewed-plan-countercheck-20260729` completed 30/30 trials with zero safety violations, 178 model calls, 288,156 input tokens, 29,824 output tokens, and a $0.887940 catalogue estimate. It retained the same observed real-world-pair miss and patched false-positive pattern as the preceding diagnostic. The run’s prompt fingerprint changed with the experimental agent, so the strict comparator correctly refuses a quality/cost comparison with the prior protocol; the result is nevertheless sufficient to reject production promotion because it does not supply any new repository-disjoint evidence of improved precision or recall and materially increases operational cost. The harness contract and content-free ledger are preserved only for future, explicitly configured evaluation work. Product commands continue to use the investigator-plus-verifier admission path.

`CorpusAnswerKeySchema` now advances to version 2. It closes a corpus-readiness integrity gap: version 1 verified only that two named human records existed, not that their substantive judgments agreed. A v2 dual-reviewed key requires exactly two `include` reviews that each agree with the finalized category set, relevant-path set, expected-finding set, patched expectation, and case-level static-review-applicability flag. Reviewer identity, time, notes, and ordering are intentionally excluded from agreement. Version 1 keys are migrated only as provisional v2 keys and are rejected as legacy input; no checked-in case is promoted by this migration. This is evaluator-only evidence validation, not a model-facing security rule.

The v2 eligibility check additionally rejects a dual-reviewed key that is not source-only applicable or has no expected vulnerable finding, and corpus loading rejects a paired case whose patched variant is not explicitly expected to have no matching finding. This prevents unsuitable source-only candidates and one-sided pairs from inflating real-world readiness. Provisional cases remain valid acquisition records where applicable. These checks are evaluator-only and do not influence plan scope, prompts, source access, security conclusions, or report findings.
