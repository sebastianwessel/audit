# Evaluation runner and report

## Execution model

The evaluator runs locally with no target network and no target execution. It validates the pack, copies or mounts an agent-visible fixture view inside a temporary jail, runs the normal plan/audit/report workflow with a fake or configured provider, then scores the validated report using trusted code. Answer keys and scorer modules are outside the agent sandbox and are never registered as Purista tools.

The runner must support `fixture` mode by default and `benchmark` mode only when an explicitly named offline pack is present. A live-provider flag is opt-in, requires credentials outside artifacts, and is rejected in the default CI environment. Failed, cancelled, incomplete, and safety-violating runs all remain visible in `EvaluationRunSchema` and cannot be coerced to a clean pass.

Before a paid evaluation can construct a provider, open a target/corpus, write an artifact, or dispatch a model call, its shared no-network preflight validates each selected route's declared structured-output profile against every live output contract. The source-free result exposes only route identity, compatible/not-compatible state, stable failure code when needed, and protocol/schema fingerprints. A profile change is part of evaluation identity, so incompatible historical work is rejected rather than resumed under different transport semantics. Provider transport envelopes are lossless request/response adapters only: canonical feature contracts, reports, checkpoints, and scores never contain them.

An evaluation debug option may explicitly enable a separate private diagnostic sink for provider failures. It is disabled by default, written atomically only below ignored evaluator-private work, recursively redacted, and limited to allowlisted source-free error metadata. It never changes a terminal trial state, model observation, cost ledger, score, baseline, comparison, checkpoint reuse, or public artifact. A failed private write is deliberately best-effort and has no guaranteed durable marker: the same unavailable destination cannot truthfully promise to record its own failure. It cannot replace or otherwise alter the underlying evaluation result.

## Artifacts

Each run writes atomically:

- `evaluation-run.json` with configuration, digests, lifecycle, counters, per-case outcomes, metrics, and gate status;
- `evaluation-report.md` as a deterministic human projection;
- `case-results.jsonl` with one validated, source-free result and ordered execution trace per trial.

Each trace event identifies only a completed model response or a completed/rejected repository-tool operation. It records ordinal, operation id, timing, numeric usage/cost or returned-byte count, and a stable error code. Trace events never contain source paths/content, context, prompts, answer keys, provider request ids, tool arguments/results, secrets, or raw model output. The report renders a human-readable per-trial flow; `case-results.jsonl` is the complete queryable record.

Private debug diagnostics are not trace events and do not appear in `evaluation-run.json`, `evaluation-report.md`, `case-results.jsonl`, source-free checkpoints, or public output. They are diagnostic-only operational help, never quality evidence.

A provider-backed trial may call no outcome `completed` until every reached stage has completed its feature-owned canonical output projection. If a model response is structurally usable by the harness but fails a later deterministic projection or audit continuation, the trial retains that active stage's complete source-free observation, marks the phase/trial failed with its stable projection code, and retains the exact observed-cost contribution. Expected-evidence diagnostics must distinguish a stage that was not reached from a reached stage whose terminal projection is unavailable; they must not attribute the latter to a mapper, posture, or model miss. New evaluation artifacts reject a missing active observation or a model-cost aggregate that cannot be reconstructed from the retained/reused stage ledger. Historical artifacts that predate this invariant are diagnostic records only and are never comparable quality evidence.

## CI behavior

CI runs schema/fixture validation, safety fixtures, fake-provider end-to-end conformance, scoring, and report projection checks. It does not require provider credentials or network access. The provider-free `bun run eval` command is a harness-isolation smoke check: its intentionally blank responder records an incomplete semantic-plan measurement and exits successfully when no safety violation occurs. `bun run eval:corpus:integration` is separately named deterministic corpus integration: it validates corpus isolation, source-tool lifecycle, and artifact projection, and cannot measure a security finding, recall, precision, or model quality. The fixture suite also proves one complete reviewed-plan lifecycle and an exact no-dispatch resume, but deliberately uses a non-adjudicated source location and requires a failed diagnostic gate; it is protocol evidence, never a model-quality or security result. The targeted provisional seed has no checked-in precision baseline. Baseline thresholds belong only to an explicit provider benchmark and an exhaustive reviewed baseline with matching coverage class, pack, profile, and route. They fail when a hard safety gate fails, a required case is missing, a report is invalid, a critical/high case becomes an unreviewed miss, or an exhaustive-qualified aggregate threshold regresses. Baseline changes require a dated review note and a new evaluation report.

For every generated-plan trial, the normal evaluation runner invokes its evaluator-owned semantic-plan operation only after the product workflow has reached a terminal result. The operation checkpoints the exact run/trial/plan/rubric/route binding below the private evaluator work root and returns one of completed, incomplete, or cancelled; the product result remains unchanged if the evaluator cannot finish. A `planning-generated` profile intentionally stops after plan generation and semantic measurement, so planning evidence can be collected before optional audit cost; it never constructs audit coverage, candidate funnels, retained audit output, or finding scores. Its trials have no reviewed-plan binding and cannot carry audit fields. Conversely, an `audit-reviewed-plan` trial requires its evaluator-owned reviewed-plan fingerprint and cannot carry generated-plan keys or path reachability. The reviewer-owned plan must phrase each obligation to discriminate the expected vulnerable behavior from its paired patched behavior: it names the protected consequence and the source relationships/controls required to establish or negate it. It is never generated from an answer key or widened after a trial result. There is no standalone semantic-adjudication command or secondary report lifecycle. `EvaluationRunSchema` v13 records each trial state and a derived `measurementState` with `workflow`, `semanticPlan`, and `finding` dimensions. A generated-plan diagnostic gate may pass only when every selected trial completed, all declared relevant paths are reachable, every semantic-plan measurement completed, and each measurement reports complete expected-scenario coverage and no unrelated enabled vector. That gate is a bounded diagnostic-pack result only: it is neither product admission nor a provider-quality, reliability, or release claim.

## Implementation placement

The evaluator is an isolated `evaluation/` workspace with exactly three ownership roots: `src/` for evaluator-only TypeScript and colocated tests, `data/` for versioned evaluator-only fixtures, corpus packs, acquisition metadata, curation dossiers, and stage-isolated packs, and `runs/` for ignored generated output. Product code must not import `evaluation/src/`; evaluator data is never mounted with answer keys into an audit agent. Cross-feature execution tests belong under `tests/integration/` and `tests/e2e/`; shared support helpers belong under `tests/support/`.
