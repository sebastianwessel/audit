# Control and state corpus expansion

Status: approved acquisition plan for CAP-056. It creates no runtime download, target execution, exploit, patch application, or automatic source inclusion.

## Goal

The current seed has only one real-world paired project and cannot establish provider reliability. Its single real dynamic-state pair is useful for diagnosis but cannot justify a model or prompt decision. This plan builds a repository-disjoint development corpus that separates real-world reliability evidence from synthetic control regressions.

## Required development matrix

The first expansion contains at least 30 real-world paired projects and at least three real-world language families. No repository may occur in more than one split or contribute more than one selected case; a vulnerable/patched pair is one case. The reviewers must deliberately seek the following semantic control families; a missing family remains a readiness gap rather than a fabricated example.

| Family | Required source evidence | Pair requirement | Minimum real-world pairs |
| --- | --- | --- | ---: |
| Dynamic state and ownership | State mutation or lookup plus the relevant ownership, dangerous-key, or boundary control. | Patched variant changes or establishes the control without only renaming symbols. | 5 |
| Authorization and tenancy | Subject/object relationship plus authorization or tenant isolation control. | Patched variant adds or corrects a source-supported authorization decision. | 5 |
| Validation and canonicalization | Untrusted input transformation plus an allowlist, parser, canonicalization, or bounds control. | Patched variant materially changes the controlling condition. | 5 |
| Sensitive data handling | Sensitive-data source plus a storage, log, transport, or redaction boundary. | Patched variant removes exposure or adds a verifiable control. | 5 |
| Unsafe operation and memory/resource bounds | Sensitive operation plus size, lifecycle, or error-handling control. | Patched variant repairs the relevant bound/lifecycle condition. | 5 |
| Injection or outbound trust boundary | Construction or outbound operation plus parameterization, encoding, or destination control. | Patched variant changes the source-visible safety boundary. | 5 |

The matrix is a sampling target, not a semantic rule catalogue. It never tells the product what is vulnerable; it only makes the evaluation corpus broad enough to measure whether the product can reason about those source-supported situations.

## Offline acquisition sequence

1. A contributor begins with a metadata-only candidate registry. It contains only pinned upstream record references, revisions, record digests, and the upstream source-license status observed for that lead; it contains no source-snapshot state, human-adjudication state, source snapshot, expected category, location, CWE, plan, or answer key. The closed source-pair workspace is the sole authority for an acquired snapshot, and the strict corpus answer key is the sole authority for human adjudication. `bun run eval:candidates` validates the checked-in registry; `bun run eval:candidates --source <already-local-openssf-checkout>` additionally verifies every selected metadata record without network access. The verifier canonicalizes the local source root and every metadata path; malformed JSON, final-file symlinks, and parent-directory symlink escapes fail closed.
2. `bun run eval:acquire -- --registry <registry> --candidate <id> --repository <already-local-git-repository> --output <directory>` may materialize one complete source pair. It reads only local Git objects, verifies the selected candidate's registry binding and exact vulnerable/patched revisions, preserves every tracked regular file with its mode and byte digest, and publishes an atomic manifest below the supplied output root. A published workspace contains exactly `snapshot.json`, `vulnerable/`, and `patched/`; missing or unexpected entries, unsafe paths, symlinks, submodules, non-regular tracked entries, and later tampering fail closed. It does not fetch, execute, build, test, label, review, or expose source to a provider. Its manifest has no answer key, expected finding, classification, urgency, source excerpt, review state, or model-visible path. Copying the candidate's `sourceLicenseStatus` is provenance only, not a license or inclusion decision.
3. `bun run eval:acquisition-snapshots` revalidates every checked-in acquisition workspace without using a provider, a target jail, or an answer key. It accepts only the documented root readme and non-symlink workspace directories; it rechecks each pair's manifest and every copied byte/mode, rejects duplicate snapshot or registry/candidate identities, and prints only content-free snapshot summaries. It neither updates a candidate registry nor changes corpus, readiness, baseline, or source-inclusion state.
4. A contributor records upstream URL, immutable revision, archive or source checksum, retrieval date, license, attribution, and a source-inclusion decision for every dataset and project.
5. For a low-cost internal development key, one traceable source-only AI-assisted reviewer records expected finding identity, source-visible role-specific evidence ranges, static-review applicability, patched expectation, semantic control family, and exclusion reason when applicable. Its key remains targeted and is run once by default. Two independent human records are optional stronger evidence and are required only for a later external reliability claim; two names alone do not establish dual review.
6. A resolver records disagreements without replacing either original review. A provisional case may support exploration but cannot set a baseline or gate.
7. The local pack passes `eval:import`; that command validates checksums, licenses, project/split uniqueness, answer-key isolation, and no-overwrite behavior without network access.
8. The importer writes only a content manifest and source-only target views. Answer keys, reviewer notes, source patches, and acquisition metadata remain evaluator-only and are never mounted for an agent.

## Exclusions

- Do not import a case because a benchmark label or patch name appears attractive.
- Do not use a patch hunk as the model's prompt or as a finding-admission rule.
- Do not run targets, builds, tests, containers, exploit scripts, or network calls to validate a case.
- Do not count synthetic, semantic-regression, provisional, duplicate-repository, or non-paired cases toward real-world readiness.
- Do not publish source code unless its recorded license and inclusion decision permit it.

## Readiness and promotion

CAP-056 is complete only when the imported pack's source-free readiness report proves the 30-project development matrix, dual review, three real-world language families, and the required control-family coverage. A provider result then remains development evidence until a private holdout exists. The 100-project/25-patched-negative reliability threshold remains unchanged.
