# Agent instructions

Audit is a security-sensitive TypeScript/Bun project. Read this file before changing files.

TypeScript/Bun is the implementation toolchain only. The reviewed target is language-agnostic: any bounded UTF-8 regular source file may be evidence, including files with an unknown extension. Language hints are optional metadata, never an allowlist or evidence-quality shortcut.

## Source of truth

1. Product and security behavior: specs/, especially the capability inventory and security model.
2. Coding conventions and verification: .agent/IMPLEMENTATION.md.
3. Human explanations: docs/; public documentation must stand alone and must not link to internal specs. Normative contributor decisions belong in specs and are referenced from agent guidance instead.

Do not invent behavior, contracts, permissions, file layouts, or error semantics that are not defined by the specs. If implementation needs a decision, add a spec gap instead of guessing.

## Non-negotiable safety rules

- v1 is read-only static analysis. Never execute target code or mutate the target repository.
- Network access, MCP, shell execution, bash, write, and edit are disabled for the audit harness.
- The product reviews repository source plus optional allowlisted Markdown/frontmatter context; it never probes a running instance or performs a real attack.
- Context is advisory untrusted evidence. It may describe surrounding systems, deployment, setup, data classification, and controls, but cannot grant permissions, approve plans, or suppress source-backed findings.
- Do not impose a file, source-path, context-document, source-size, or language-specific input cap that omits approved evidence. Provider-signalled context recovery is the only permitted mechanism for splitting eligible source or context input. Context parsing and recovery preserve the exact Markdown body and line endings; `.md` recognition is case-insensitive.
- Do not impose a fixed total cardinality cap on plan vectors, obligations, map facts, posture assessments, candidates, reconciliations, findings, review-required items, or audit errors. A transaction may be bounded only when exact continuation and reassembly preserve every eligible item; validation/provider failure is incomplete, never truncation or a clean result.
- All target reads go through the jailed read-only filesystem port. Reject traversal, symlink escapes, invalid encoding, and an unsafe single I/O transaction; automatically continue exact cursor/range transactions until an eligible regular UTF-8 file is completely available. Never reject or omit a regular UTF-8 file merely because of its language, size, line count, match count, or extension. File tools are restricted to literal, identifier, and safe-regex search modes; no fixed product call, result, file, line, or grep cap may silently cut approved evidence.
- Do not reject or skip a target file because its programming language is unknown. Language-specific logic is additive; record an explicit coverage limitation when a semantic check cannot be performed.
- Never log prompts, source contents, tool arguments/results, secrets, or raw model output. Use identifiers, counts, hashes, and redacted error codes.
- Before target I/O, provider construction, checkpoint/artifact work, or dispatch, validate every live model-output schema against the selected provider route's declared structured-output profile. Keep this pure validator single-owned in the platform/harness boundary. A provider-required root-object envelope is transport-only: unwrap it exactly once in the owning stage before canonical feature materialization; never persist it or let it alter finding admission, scoring, reports, or checkpoints. An undeclared/incompatible profile fails closed and changes the exact workflow identity.
- Evaluator-only provider-failure diagnostics are opt-in, private, atomic, source-free, and non-scoring. They may retain only allowlisted identifiers, timings, fingerprints, stable error categories/codes, retryability, and the closed normalized provider metadata fields (provider, model, method, reason, HTTP status, provider code) below ignored evaluator-private work. They never retain provider messages, request identifiers, headers, bodies, prompts, source, tools, credentials, model output, normal evaluation artifacts, public artifacts, observations, baselines, comparisons, or checkpoint reuse; a diagnostic-write failure cannot change the underlying result.
- Model usage and catalogue-derived cost are source-free telemetry, not an execution gate. A resumed evaluator deduplicates byte-identical retained stage observations so an orphaned checkpoint and its enclosing trial do not double-count usage or cost in reports.
- A provider-evaluation or one-case smoke command writes a source-free command checkpoint before audit dispatch. Its run id is immutable: a fresh command rejects an existing checkpoint, and resume requires the exact sealed input identity. A known stopped command closes as failed or cancelled rather than remaining running; command state never rewrites retained vector or trial outcomes.
- Audit execution accepts one strict plan artifact whose target and context fingerprints match the current input. Human plan review, editing, ownership, and approval workflow are outside the product; do not add approval state, reviewer metadata, or an approval bypass.
- Additional observations are planner output for human review only. They never execute, create a finding, carry priority/fix text, affect coverage, CI, or evaluation scoring. Only explicit promotion of an exact sealed-base observation through the plan draft/reseal workflow may convert it into a normal enabled vector.
- Per-vector recovery checkpoints are written only below the separate output root. A validated source-minimal evidence map is checkpointed before candidate-blind source posture, and completed evidence-map, source-posture, or canonical candidate-grounding context-overflow children may additionally persist an exact-bound validated source-minimal phase leaf before the matching topology completion event. A canonical candidate-grounding draft is checkpointed before verification, each candidate-aware verifier/countercheck unit checkpoints `pending`, `running`, then its source-minimal completed decision, and a terminal vector result is written afterwards. A grounding leaf and draft hold one canonical per-seed `grounded`, `null`, or `binding-rejected` outcome; neither retains a discovery seed or raw model selectors. The draft retains validated closures, complete source-free discovery/grounding funnels and candidate-rejection ledger, and the two required phase observations. One feature-owned pure resolver chooses the smallest exact incomplete boundary: a matching draft is reusable even before a later candidate-aware checkpoint exists, preserves its durable grounded candidates and upstream observations, and schedules only the normal missing candidate-aware unit or explicitly retryable seed work. Discovery seeds, raw grounding input/output, and model-authored verifier rationale are never persisted. Bind reuse to run id, plan id, target fingerprint, provider, model, verifier route, evidence-map protocol fingerprint, complete workflow protocol fingerprint, vector id, phase, candidate ordinal/digest, candidate-grounding prompt fingerprint, and (for a phase leaf) recovery protocol plus root/child scope hashes; never reuse a mismatched result. Pending/running work is rescheduled; only a matching completed unit is reusable. Historical investigation and candidate-repair artifacts are not read.
- Reject a malformed plan or a plan whose target/context fingerprints do not match before audit-stage provider dispatch. Do not model draft, rejected, or approval states.
- Audit every enabled vector only inside its approved `scopeGlobs`. Investigator and verifier may receive only that vector's path manifest, separately labelled applicable context, and scoped read-only tools; do not add a fallback that can inspect the rest of the repository. An experimental counterchecker follows the same scope rule but is not on the production admission path.
- The production path is language-neutral: deterministic code may enforce plan identity, scope, path/line existence, normalized schema shape, redaction, phase binding, and state transitions only. It must not infer an operation, unsafe condition, data flow, exploitability, classification, urgency, or finding from a regex, API name, language hint, extension, parser, AST node, fixture, benchmark, or answer key.
- A model-facing evidence-map fact carries only its strict fact identifier, closed neutral role, statement, approved-obligation references, and exact `{path,startLine}` source selections. Deterministic provenance projection validates that selection and derives the canonical content digest, kind, and line range; source text never enters durable artifacts; never require or persist model-authored snippets, evidence kinds, roles, or end lines.
- Every enabled vector first produces a source-backed evidence map of neutral facts, observed controls, a distinct exact control-fact inventory for every approved obligation, unanswered obligations, and limitations, then a fresh candidate-blind source posture with exactly one judgment per approved risk-positive review obligation. The mapper must label every source-visible potential safeguard neutrally as a control before deciding effectiveness, and an inventory mismatch makes coverage incomplete. Every posture assessment must cite every mapped control for its own obligation before retaining a directional conclusion. Every initial or recovered phase input has no inline source package, and each source-deciding phase must receive a successful scoped `repo_read` or `repo_grep` result when its scoped manifest is non-empty; attempted/rejected calls and `repo_list` never satisfy inspection. The shared lifecycle retries an uninspected completion only inside the unchanged scope under the configured retry policy, then records `coverage-incomplete` rather than inventing a fallback or clean result. The posture input excludes candidates, findings, classifications, urgency, remediation, verdicts, answer keys, and paired-variant data. Discovery returns only bounded map- and posture-referenced seeds and closure declarations; it cannot emit a finding. Candidate grounding receives only valid seeds and may return null or a candidate that preserves its exact vector, obligations, inherited map facts, and posture assessments. It may add a validated map fact only when that fact binds one of the seed's exact approved obligations; it never drops inherited map facts or expands scope. A non-null grounding contains only a precise statement, limitations, and selected operation/unsafe-condition locations as `{ factId, evidenceIndex }` from its own validated selected map facts; deterministic code projects those exact locations and assigns the evidence roles. The verifier still independently reads source and decides the result, but an accepted verifier result also selects its operation, unsafe-condition, control, exact plan-obligation reconciliation, and posture-reconciliation evidence from that bounded map basis. It must explicitly reconcile every exact hypothesis obligation and every candidate-relevant posture assessment, and cannot leave either unresolved. An obligation reconciliation may select only a map fact that binds that same approved obligation. Deterministic code projects exact locations, the hypothesis's exact obligations, relevant mapped control identifiers, and required posture-assessment identities. This is provenance, coverage, and declared-state integrity, not a source-flow or vulnerability rule. Map/posture references retain provenance, but no synthetic origin-to-operation pointer is created or used as an admission gate. A verifier must accept, reject, or mark that same admitted hypothesis incomplete before it persists. Each relevant mapped control and posture assessment must have a verifier evidence selection at its mapped source location; an identifier alone is not proof of inspection. Counterchecks preserve those boundaries and may not introduce a different risk, vector, classification, urgency, or remediation.
- A candidate-aware verifier or countercheck may continue from an `inconclusive` posture, and a `risk-supported` posture is never proof. When a structurally accepted hypothesis conflicts with a validated, tool-inspected candidate-blind `risk-contradicted` posture over the same vector scope, route it to the source-minimal `reviewRequired` queue. Never promote it to a confirmed finding, attack chain, or CI severity decision. This is the single generic independence/disagreement signal over the same scoped model judgment; do not replace it with language, parser, source-text, corpus, or answer-key heuristics.
- Claim-selection lineage is lossless and role-specific: discovery has no claim-role selections. Canonical grounding independently selects exactly one `operation` and one `unsafe-condition` bundle of neutral `{ factId, evidenceIndex }` map selections from validated map facts bound to the seed's exact approved obligations. Accepted verification preserves every grounding selection under the same role; one selection may support both roles. This is map-reference provenance only, never source text, a semantic relation, or a deterministic finding rule.
- Discovery and grounding model schemas never contain source-posture assessment identifiers. The source-posture feature owns the single deterministic projection from approved obligations to canonical posture identifiers and their existing map facts; do not duplicate that projection in prompts, model outputs, or stages.
- Normal retry keeps the original vector scope and never permits a static fallback, broader reads, or a finding without a schema-valid verifier result. Model-facing decision unions contain only the active semantic branch; feature-owned materialization creates canonical inactive `null`/empty fields. A validation retry descriptor is single-owned and contains only the complete canonical set of static schema-path labels and its digest: validate, deduplicate, sort, and never truncate labels before digesting. Distinct canonical descriptors must never be treated as identical. Under unchanged protocol and scope, a repeated descriptor is terminal `validation-repair-no-progress`, visibly incomplete, and not generically retryable; only a fresh explicit run with changed identity may attempt again and it must not reuse that terminal result. A terminal repeated descriptor may reach an explicitly enabled evaluator-private diagnostic only. A normalized Purista `ModelError` with `meta.reason: context_length_exceeded` additionally enters the one shared deterministic source-path/range/context recovery coordinator; it never pre-splits by estimated tokens/bytes, never drops applicable advisory context, never leaks partition data, and never admits a non-losslessly reduced verifier decision. Experimental countercheck recovery follows the same rule and cannot alter a product report.
- A normalized Purista timeout or cancellation is a provider-neutral terminal stop: it receives the stable `provider-cancelled` code, is never retried by the application, and remains an explicit cancelled vector/trial eligible only for explicit unfinished recovery. Never classify it from provider text.
- Remove the current direct-flow structural-adapter experiment from the production-design path. Do not add a replacement parser or static rule to improve a fixture/evaluation result. A future AST service requires a separate spec as multi-language navigation/enrichment only; it may never determine plan scope, admission, urgency, or a security conclusion.
- Classification, urgency, confidence language, impact summaries, and proposed fixes are outside the confirmation protocol. No patch application is in scope.
- Scan lineage is artifact-only: it may read two validated report JSON artifacts through the output jail and write a source-free lineage artifact. It must not open the target, context, a provider, a model, or an evaluation answer key. It uses only the single-owned exact finding identity; incomplete/missing vector coverage is `unknown`, never new/resolved/persisting.

## Type, structure, and test discipline

- Define each external or persisted shape once as a strict Zod schema owned by its feature.
- Export inferred types with z.infer; do not write parallel interfaces or duplicate enums.
- Prefer closed objects and explicit unions. Avoid any, unknown, open records, and unchecked casts.
- Normalize model-facing enum tokens at the boundary for casing and whitespace, then store canonical lowercase values.
- Keep model/provider details behind Purista platform adapters.
- Local runtime configuration is loaded from an ignored project-root `.env` through the configuration adapter. `RuntimeConfigurationDefaults` is the sole owner of default provider/model, roots, verification mode, and concurrency, so normal model-backed setup needs only that default route's credential. Keep precedence `defaults < inherited environment < .env`; CLI inputs select one operation but must never override runtime configuration. Never parse or use provider secrets outside that adapter.
- Price values never belong in `.env` or CLI flags. Resolve costs only through the versioned bundled exact-model catalogue; its explicit contributor refresh command may use the network, but product commands and provider evaluations never do.
- `eval:provider:preflight` is the required no-network preparation path for a paid evaluation. It shares provider evaluation's route, credential-presence, exact-price, corpus, selected-population, protocol, and holdout validation, but must neither construct a provider nor write a checkpoint or artifact. Credential values remain inside the provider-resolution adapter; its content-free result may expose only the environment-variable name and readiness boolean.
- Keep every unit test beside the implementation it verifies; reserve top-level tests/ for shared fixtures, integration, and end-to-end scenarios.
- Evaluation fixtures and trusted answer keys stay under evaluation/ and are isolated from the agent-visible target view.
- Real-world corpus evaluation validates pinned source checksums before a provider call. Keep corpus manifests, answer keys, baselines, generated reports, and agent-visible source views separate; provider runs default to one diagnostic repeat and are never default CI work. Repeated experiments must record their selected repeat count and may report agreement/distribution only when those statistics are defined; neither repeat count nor a provider run alone establishes reliability. Do not impose a numeric upper cap.
- Evaluation contracts do not impose arbitrary collection ceilings on source entries, expected paths/findings/scenarios, generated vectors, artifacts, trial traces, or recovery attempts. They preserve complete declared data or reject an invalid shape explicitly; no evaluation subset may be silently omitted.
- A provider run's workflow finding gate is not a provider-quality claim. Persist the single evaluator-owned evidence qualification derived from corpus readiness and selected split; `diagnostic` is non-qualifying. Reject incomplete evaluation artifacts. A private-holdout result additionally requires an externally managed, source-free Ed25519 attestation that binds the isolated holdout pack manifest to a frozen readiness decision; persist only its minimal reference, never the source, answer key, readiness report, or private key.
- Evaluation summaries must expose minimum and median fully evidenced finding recall, partial-evidence recognitions, vulnerable false negatives, and patched/benign false positives. A partial role overlap is diagnostic only and must not count as a detected expected finding or pass a workflow gate. Aggregate repeated outcomes by case and variant; do not let favourable aggregate metrics conceal instability.
- Corpus candidate registries are metadata-only acquisition leads. They may bind local upstream metadata to revisions, digests, and observed upstream source-license status, but never create a corpus case, source-snapshot state, human-adjudication state, answer key, readiness count, model input, or provider-quality claim. Closed source-pair workspaces own acquired-snapshot state; strict corpus answer keys own human adjudication.
- `evaluation/data/curation/dossiers/` is a separate evaluator-only source-preparation layer. It may bind a validated acquired pair to advisory provenance, a source-only review question, source anchors, scope limitations, and a paired-negative condition, but is never agent input, an answer key, a deterministic security rule, or readiness evidence. Keep the acquisition workspace closed and require a separately isolated corpus copy, schema-valid key, and reviewed plan before provider measurement.
- A schema-v6 `ai-assisted` answer key binds one traceable source-only development review and supports one internal diagnostic run only; it cannot support whole-repository precision, external reliability, independent validation, provider selection, or a readiness gate. Only paired real-world cases with a stronger `dual-reviewed` answer-key record count toward the corresponding pilot or reliability readiness. Its two distinct human `include` records must agree with a source-only-applicable expected vulnerable finding, finding-label coverage class, finalized source-bound planning scenarios, patched expectation, and static-review-applicability judgment; the paired variant must explicitly expect no matching finding. A scenario has a stable id, one-or-more relevant paths, and explicit expected-finding ids bound to those paths. Generated-plan scoring measures path reachability only; it makes no automatic semantic-plan-quality claim. Provisional cases may be reported as acquisition progress but cannot satisfy pair, patched-negative, language, control-family, or private-holdout gates.
- Provider evaluation has three non-comparable profiles: `planning-generated` measures planning only, `audit-reviewed-plan` loads a strict evaluator-owned plan and measures audit behavior only, and `end-to-end-generated` measures both stages. Answer keys never construct reviewed plans. An optional evaluator-only case selector must resolve inside the selected split before model dispatch, execute every declared variant, and bind run/checkpoint/report identity; it never reaches the agent-visible target. Record the profile and selector in each run, checkpoint, report, and comparison identity; reject cross-profile or selector-mismatched comparisons.
- A generated plan's immediate evaluation score is path-scope reachability only. Semantic plan quality requires a separate evaluator-only AI-assisted adjudication bound to the exact run/trial, plan id/digest, target/context fingerprints, answer-key scenario digest, evaluator protocol, and route. It receives only the sealed plan and source-free evaluator rubric after product work ends; it has no target source or repository tools. Validate its complete bidirectional scenario/vector closure structurally, checkpoint source-free lifecycle observations, and derive metrics only from that mapping; never infer semantic equivalence from model wording, categories, source, language, parsers, benchmark labels, or answer-key content. It cannot alter product admission.
- Model operations are single-owned in `src/features/model-operations/`. Record one content-free observation for every planning, evidence-mapping, source-posture, investigation, verification, plan-semantic-adjudication, and experimental countercheck call, then derive the run aggregate from those stages. A newly written stage also retains one contiguous ordered trace of completed model responses and completed/rejected repository-tool operation ids, timings, numeric usage/cost or returned-byte counts, and stable error codes; validate it exactly against the request and tool aggregates. Do not implement an application prompt cache or persist prompts, source, tool data, credentials, request ids, or raw model output. The only exceptions are feature-owned, validated, artifact-text-redacted semantic summaries on canonical map facts and posture assessments, and `ClaimNarrative` in a canonical grounded hypothesis/report finding. They are bounded semantic context, never transcripts, source excerpts, evidence, identities, or admission inputs; map/posture summaries are included in their dependency fingerprints and never published. An unavailable cost is never zero.
- Every feature root owns an `index.ts` for its broad public surface. Cross-feature consumers use only a deliberate facade: a feature root or a topic's `index.ts`, `agent/index.ts`, or `stage/index.ts`; they never deep-import implementation files. Agent facades are construction-safe contracts/instructions only; executable stages have a separate stage facade so harness construction cannot create a runtime dependency cycle. Keep an agent's contract, instructions, stage-specific policy, schemas, and tests inside the topic feature that owns its semantics (for example `attack-planning/planner/`); model-facing repository-tool schemas/descriptions are single-owned under `src/features/review-workflow/tools/`. The exact common scoped lifecycle is single-owned by `review-workflow/stages/scoped-model-stage.ts`; it owns only scoped tools, session/retry lifecycle, and the content-free observation—not agent semantics, approvals, or report admission. The Purista platform adapter may mount `repo_list`, `repo_read`, and `repo_grep` with safe handlers but must not duplicate their schemas or prompts.
- The `eval:import` contributor command accepts only already-local packs. It must remain network-free, reject overwrite/symlink/checksum/license failures, and write a content manifest via temporary output; it is never a default CI action.
- Move code into src/shared/ only when two features need the exact same invariant behavior.
- New attack vectors declare stable explicit review obligations; never infer a question/criterion matrix from indexes. A persisted finding must include complete verified source-evidence bundles and is either `accepted` or `needs-review`; reports do not construct attack chains from co-location. A verifier rejection needs source-backed contradiction evidence and is a completed negative decision, while a model `incomplete` result and an operational failure remain incomplete coverage. Vector coverage exposes one source-free closure row per obligation, map/posture counts, each phase's own stage observation, the balanced admission funnel, and the discovery-to-grounding funnel, including a closed reason ledger for rejected discovery and grounding bindings. A source-backed `not-applicable` closure has a crisp required reason and is neutral: it is neither a finding nor a passed check. `no-source-backed-candidate` never means deterministic safety; incomplete or not-reached obligation closure prevents completed coverage. Do not silently read an earlier report/checkpoint as discovery-and-grounding evidence-first data.
- A completed new-format evaluation trial aggregates its feature-owned vector admission and hypothesis-grounding funnels for diagnostic reporting only. Do not duplicate those definitions in evaluation code, store reasons/source/model content, or use funnel counts to alter labels, scores, prompts, plans, or finding admission.
- Current persisted artifact schema versions are owned by their strict feature schemas. `specs/04-contracts/01-artifact-contracts.md` contains the sole normative version registry; reject a mismatched artifact rather than translating or treating a prior version as equivalent.
- The verifier-tool-evidence funnel counter is reserved for isolated evaluation experiments. The two-observation control-path experiment did not meet its promotion evidence and is not on the product admission path.
- CAP-063's independently routed verifier is evaluation-only. It requires strict distinct-route configuration, route-bound checkpoints, route-labelled stage telemetry, and versioned artifacts. Do not enable it for product admission or make a quality claim before the qualified-corpus promotion contract is met.

## Agent roles

Role-specific guidance lives under .claude/agents/. Those files may explain sequencing, but cannot override the specs or this file.

## Required checks

```bash
bun run spec:check
bun run typecheck
bun run lint
bun test
bun run test:coverage
bun run eval:corpus:integration
bun run check
```

Use focused tests first, then the full check before handoff. Do not add live-provider tests to the default suite; gate them explicitly behind credentials and an opt-in environment variable.
